\section{Concurrency Conflicts and Proposed Solutions}

Several concurrency conflicts were identified in the booking and maintenance workflow.

\subsection{Conflict 1: Booking while maintenance begins}
A booking transaction may read a room as available while a maintenance transaction is changing the room status to unavailable.\newline
\textbf{Proposed solution:} enforce atomic booking validation and re-check the room state before final confirmation. A transaction with at least Read Committed isolation should be used.

\subsection{Conflict 2: Starting and canceling a reservation}
A reservation may be checked in while another transaction cancels it.\newline
\textbf{Proposed solution:} enforce state-transition rules so that a reservation can only move to a new status when its current state matches the expected value.

\subsection{Conflict 3: Multiple reviews for the same booking}
Two approval transactions may review the same booking at the same time.\newline
\textbf{Proposed solution:} serialize review creation or enforce a uniqueness check plus a state check before inserting the review.

\subsection{Chosen Isolation Level}
The project adopts \textbf{Repeatable Read} as the appropriate isolation level. It provides stronger consistency than Read Committed while avoiding the overhead of Serializable isolation for ordinary operations.

\section{Indexing and Query-Tuning Results}

\subsection{Indexes Proposed}
\begin{lstlisting}

ON BookingRequest (requested_start_time, requested_end_time);

\subsection{Interpretation}
Indexes bring the largest benefit to operations involving time-range filtering, table joins, and status-based lookup. In contrast, simple CHECK constraints do not improve much because they are evaluated directly on each row and do not require scanning large amounts of historical data.

\section{Functional Dependencies and 3NF Verification}

To verify the schema, the group analyzed candidate keys and functional dependencies for the main operational tables.

\subsection{Representative Functional Dependencies}
\begin{itemize}
    \item \textbf{Space}: $space\_id \rightarrow space\_name, space\_type\_id, building, floor, room\_number, capacity, space\_status\_id, space\_policy\_id$.
    \item \textbf{User}: $user\_id \rightarrow surname, given\_name, email, phone\_number, user\_role\_id, department\_id, user\_status\_id$.
    \item \textbf{Facility}: $(facility\_type\_id, facility\_sequence\_number) \rightarrow facility\_name, space\_id$.
    \item \textbf{BookingRequest}: $booking\_request\_id \rightarrow user\_id, space\_id, requested\_start\_time, requested\_end\_time, purpose\_id, expected\_participants, request\_state\_id, advisory\_acknowledged$.
    \item \textbf{Review}: $review\_id \rightarrow booking\_request\_id, reviewer\_id, request\_decision\_id, decision\_time, decision\_note, rejection\_reason$.
    \item \textbf{Reservation}: $reservation\_id \rightarrow booking\_request\_id, reservation\_status\_id, usage\_note$.
    \item \textbf{Maintenance}: $maintenance\_id \rightarrow technician\_id, space\_id, reporter\_id, maintenance\_description, maintenance\_start\_time, maintenance\_end\_time, maintenance\_status\_id, result\_note, maintenance\_impact\_level\_id$.
\end{itemize}

\subsection{Why the Schema Satisfies 3NF}
A table is in Third Normal Form if it is in Second Normal Form and every non-key attribute depends only on the key, the whole key, and nothing but the key. In the operational tables above, the primary keys are simple or composite keys, and the non-key attributes depend only on those keys. There are no partial dependencies or transitive dependencies among non-key attributes, so the schema satisfies 3NF for the major operational tables. Reference tables also satisfy 3NF because they have a simple key and descriptive attributes only.
